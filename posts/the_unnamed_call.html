The Unnamed Call

How two shared libraries actually talk to each other, and the exact point where a call graph quietly gives up.

Last week I was hunting bugs in a stripped aarch64 media plugin and our pipeline kept reporting something that could not possibly be right. Every ranked function had zero reaching entries. Not a few of them. All of them.

My first guess was a bug in our own reachability code, because that is usually the right guess. It was not a bug. The library honestly had no entry points that our analysis could see, and working out why took me back through the question of how two shared libraries actually talk to each other at runtime. I thought I knew this one well, and it turned out that I knew only the easy half of it.

So these are my notes, written while they are still fresh. If you work on binary analysis, or you teach a systems course and want a concrete reason why static analysis is hard, I think there is something useful here.

Two ways to run somebody else's code

If library A ends up executing a function that lives in library B, there are exactly two ways that could have happened. I had always known both of them, and I had just never had to care about the difference until this week.

By name

A referred to B's function by its name, which means that either the compiler saw a declaration in a header and the linker recorded the dependency, or the program called dlopen and then dlsym("foo") at runtime. The route differs but the essential thing is the same in both cases- a name gets resolved, and somebody has to do the resolving. That somebody is the dynamic linker.

And because the linker has to do work, the work leaves evidence sitting in the file: an undefined symbol in .dynsym, a DT_NEEDED entry naming the library, a PLT stub, a relocation, and our tooling reads all of it, so this is the comfortable case.

By address

B handed A a number, which is to say that B stored the address of one of its own functions into a piece of memory, and A later read that number and called it. The roles are exactly as before- A is still the one doing the calling, and B still owns the code that ends up running.

That is the whole mechanism. Nothing is resolved, because there is no name to resolve. The dynamic linker is not involved at all- it has nothing to do, and it never learns that the relationship exists. No undefined symbol, no relocation, no PLT entry, nothing in any table. The only trace anywhere is a single store instruction inside B.

The difference matters for exactly one reason. In the first case something resolved a name and the resolution is recorded. In the second case nothing was resolved, so there is nothing to record, and a tool that learns about the world by reading tables learns nothing at all.

What the plugin actually does

The library I was looking at is an Android media extractor plugin. The structure is public, it is part of AOSP, so we can describe it honestly without naming the vendor build. The framework finds plugins in a directory, and for each one it does precisely this- dlopen the file, then dlsym for one symbol called GETEXTRACTORDEF. One name. That is the entire named relationship between the framework and the plugin. In the terms we used above, the framework is A and the plugin is B.

Here is what that one exported function decompiles to (vendor string elided):

void GETEXTRACTORDEF(undefined4 *param_1)
{
  *param_1 = 3;                                 /* def version */
  param_1[5] = 2;
  *(char **)(param_1 + 6) = "... Extractor";    /* display name */
  *(code **)(param_1 + 8) = android::Sniff;     /* a function ADDRESS */
  *(undefined ***)(param_1 + 10) = &PTR_DAT_001640e0;  /* a TABLE address */
  return;
}

Look at what this function does, and more importantly at what it does not do. It does not call anything. It writes five words into a struct that the caller allocated and passed in, two of those words are addresses of code, and then it returns.

So when the framework calls those addresses later, it is calling into the plugin along a path that the plugin never expressed as a call. Follow the table address and you reach the factory, which is where it gets properly interesting:

void android::CreateExtractor(undefined8 param_1)
{
  this   = operator_new(0x160);
  puVar1 = operator_new(0x10);
  *puVar1 = &PTR__Box_001605b8;            /* install a vtable */
  puVar1[1] = param_1;
  MPEG4Extractor::MPEG4Extractor(this,puVar1,(char *)0x0);
  puVar1 = malloc(0x48);
  *puVar1   = this;
  puVar1[1] = wrap(...)::{lambda(void*)#1}::__invoke;
  puVar1[2] = wrap(...)::{lambda(void*)#2}::__invoke;
  puVar1[3] = wrap(...)::{lambda(void*,unsigned_long)#1}::__invoke;
  /* ... and so on, eight of them */
}

The factory allocates the C++ object, then builds a second struct full of lambda thunks that forward to that object's virtual methods, and hands that out. The framework never touches a vtable slot directly. It calls a thunk, the thunk calls the virtual method, and the virtual method is where the parsing code (and the bug) lives.

At this point we went and counted, because we wanted to know what a tool could possibly have seen, and the numbers turned out to be worth looking at.

One row in there deserves a word, because at first glance it contradicts the figure above. The figure shows dlopen and dlsym, and the table says this library calls neither of them. Both are true, because the framework is the one performing the dlopen and the dlsym, and the plugin is the object of those calls rather than the one making them. That carries a consequence which I had not properly appreciated until I wrote it out, namely that the named half of this whole relationship is recorded in the framework's binary, where the string "GETEXTRACTORDEF" and the call to dlsym actually sit. It is not recorded here at all. So an analyst holding only the plugin cannot tell which of its exports the framework is going to ask for, or even that one of them is special.

Two of those lines took me a while to accept. The export reaches exactly one function, because GETEXTRACTORDEF makes no calls at all, and so a forward walk from the only meaningful entry point covers exactly one node out of 840.

The other one is the missing interface import. I had gone looking for an imported base class, something like a vtable symbol for the framework's extractor interface, on the assumption that a plugin implementing an interface must depend on wherever that interface is defined. There is no such import. The reason is almost funny- MediaExtractorPluginHelper is a header-only C++ class, so it gets compiled into the plugin. That is why the recovered class owner for one of the vtable slots came back as android::MediaExtractorPluginHelper at a perfectly local address. The plugin has no link-time dependency on the interface whatsoever. The "interface" is a struct layout that both sides agreed on at compile time, plus one dlsym'd name.

So the call graph we build is not wrong, exactly, it is just a graph with an island in it.

I am going to steal this for teaching. It is a very clean exercise- give the class a small plugin and its host, ask them to draw the call graph from readelf and objdump alone, and then ask them to explain how the host ever runs the plugin's parser. The gap is discovered rather than announced, which is the way I like to introduce a topic. The usual lesson about "function pointers are hard for static analysis" never really lands, because everybody nods at it. Seeing an island in your own graph lands.

Four ways a function pointer breaks a call graph

Once I had this straight, it was worth sorting the general case out, because function pointers do not break a call graph in one way. They break it in four, depending on which side of the boundary the pointer is written and which side it is called. The four cells need genuinely different machinery, and conflating them is how you end up building the wrong fix. I had been conflating two of them for years, honestly.

Our existing machinery handled the top-left cell and handled it well. A function passes &callee to a registrar, the registrar stores it into one struct field, a later call through that field dispatches to it, and we recover the edge. That is the classic callback case and it is the one everybody thinks of.

It could never have helped here, and it is worth being precise about why. First, it found zero such edges in this library. Second, and this is the part I had not thought through properly, even if it had found some, the backward search still has to terminate at an export, so adding edges to a graph whose only export makes no calls still gives you nothing. The fix for a missing root is not more edges.

The names were never there to begin with

One more thing fell out of this, and it is the part that I think generalises furthest beyond my particular problem.

Our whole reachability layer is keyed on function names. You ask it what reaches parse and it answers. So we went and checked what a name actually identifies in this library, and the answer is that it does not identify very much at all.

When our tool says it found a route to parse, it has named 21 different functions at once. That is not a small imprecision, it is 62% of the library.

And here is the bit I found genuinely satisfying. Those 24 functions called __invoke are not badly named by accident. They are anonymous lambdas, and they were never given names, because the C++ that produced them never needed one.

We went and checked what the file itself carries, since the decompiler does print a long spelling for them. There is no .symtab and there are no debug sections, only a 192 entry .dynsym, and the text __invoke does not occur anywhere in the binary at all. So that long name is not being read out of any symbol the compiler left behind. What the file does carry is AOSP source paths and assertion text- MPEG4Extractor.cpp:9273 CHECK(mBuffer != NULL) failed. and 66 others like it- which is the __PRETTY_FUNCTION__ material that the CHECK macros embed, and that is the only place in the whole file where such a signature exists. Meanwhile the record our own extractor writes for that address says plainly name: "__invoke", the short form, and the short form is what the reachability layer then reads.

So the things handed across the library boundary have no usable names for the same reason that the handoff itself has no symbol- nobody ever had to say them out loud. An address is the only identity these functions have ever had.

Which settled an implementation argument we had been having. While discussing all of this with my co-engineer Claude-Opus, it proposed adding a qualified-name field to disambiguate, which is the obvious fix and would have worked for most of these cases. I had decided the other way on a related problem a while back- let the address decide, and keep names strictly for display. That decision had looked a little fussy even to me at the time. It is obviously right here, and for a reason I would not have found without going through everything above, because a qualified name is still only a name, and two template instantiations that the linker folds together will happily share one.

This is not an Android problem

It would be easy to file this under Android oddities, and that would be a mistake, because the shape is not Android's at all- it is how essentially every loadable plugin ABI works, wherein one symbol is resolved by name, that symbol hands back a table of addresses, and all the real traffic afterwards is unnamed.

  • PAM modules- pam_sm_authenticate and friends, found by name, then driven through a struct.
  • NSS modules, nginx modules, Apache modules.
  • PostgreSQL extensions- _PG_init, then hooks installed by assignment to a global function pointer.
  • COM objects, and anything else that hands out an interface pointer.
  • Binder and HAL service stubs, where onTransact is reached through exactly this kind of indirection.

In every one of those, an analyst who reads the import and export tables and then builds a call graph will get an island. The plugin is a library whose whole purpose is to be called by code it cannot name, using a protocol that is a struct layout rather than a set of symbols. I had been treating "it uses function pointers" as a nuisance to work around. It is closer to the point of the design.

So the practical lesson I am taking away is narrow but useful- when the call graph has an island, stop looking for a call you missed and go looking for a store. The instruction that hands the address out is the edge.

I had built one of these myself

When I had all of the above straight, something kept nagging at me, and after a while I remembered what it was. I had built exactly this channel myself, years ago, in VUzzer.

VUzzer fuzzes using basic-block weights that are computed statically, and a basic-block address only means something relative to the load base of the library it sits in. The Pin tool and the Python driver are separate programs in separate processes, so that load offset had to travel from the one to the other somehow. What I did was this:

/* bbcounts2.cpp - the Pin tool, running inside the target's process */
#define FILEPATH "image.offset"
ioffset   = open(FILEPATH, O_RDWR);
offsetmap = (char*)mmap(0, 18, PROT_READ | PROT_WRITE, MAP_SHARED, ioffset, 0);
/* ... then in the ImageLoad callback, for a watched library: */
std::memcpy(offsetmap, StringFromAddrint(IMG_LoadOffset(img)).c_str(), 18);
# runfuzzer.py - the driver, a different process altogether
libfd    = open("image.offset","r+b")
libfd_mm = mmap.mmap(libfd.fileno(),0)
# ... and per run:
liboffsetcur = int(libfd_mm[:18],0)

The address crosses as an 18 character ASCII hex string, which is 0x plus sixteen digits, through a shared mapping of a file on disk. There is no symbol involved anywhere, and the entire protocol is the two numbers 18 and 0, agreed between two source files that never mention one another. Analyse the Pin tool on its own and you see a write into a mapping. Analyse the Python on its own and you see a read of a file. Nothing connects the two, which is the island again, this time with a process boundary in place of a library boundary.

So yes, the shape is the same. But the place where the analogy stops is the part I find genuinely instructive, because the Python never calls that address. It compares it:

if liboffsetcur != int(config.LIBOFFSETS[1],0):
    gau.die("load address changed..run again!")

The address is not a call target at all, it is a frame of reference. The weights were computed against one load base, so if ASLR has moved the library then every basic-block address in the table is meaningless, and the honest thing to do is to refuse the run. Which means the two cases break an analysis in quite different ways- in the plugin, a missing address costs you a control-flow edge, whereas here it would cost you the correspondence between a static address space and a running one.

And that is the naming lesson arriving from the other side. An address is an identity only relative to a base, and we had to learn it again in our own crash attribution work, wherein a sanitizer report hands you a module and an offset and that has to be mapped back to a link-time address before it names any function at all. I had already solved that once with an 18 byte file and a die(), and then met it again from the opposite end, as the person trying to recover somebody else's channel rather than the person building my own.

So the family is wider than function pointers. It is any channel that carries an identity across a boundary that nothing resolves- a shared mapping, shared memory, a pipe or a socket, an environment variable, /proc, a config file naming a symbol, a serialised callback id, an RPC handle. Every one of them creates a coupling which is real, load bearing, and in no table.

The analyst's difficulty is the implementer's convenience.

So, I would say “follow the stores, not the calls”.
